# Estimate calibration — baseline (методология)

> **Что это.** Снимок исторической статистики по выполненным задачам команды в Asana,
> на основе которого можно делать risk-adjusted оценки новых задач и подсвечивать риск просрочки.
>
> **Назначение — PM-планирование.** Не performance review, не «скоринг» сотрудников. См. «Sensitivity policy».
>
> **Это методология (переиспользуемая).** Baseline (`raw_tasks.json`, `calibration-*.json`) каждая команда
> собирает свой — он содержит реальные имена и времена и в шаблон не входит (см. `.gitignore`).

## Что измеряем

Метрику «actual / estimated ratio» (точность оценки) на типичных данных **построить нельзя**
(estimate-поля почти не заполняются). Работаем с тремя поверхностными сигналами:

### 1. Velocity — длительность задачи (`completed_at − created_at`)

Распределение в днях, сегментировано по (assignee × discipline × issue_type). Outputs: P50, P80, P95, mean, max.

**Caveat 1:** это календарная длительность жизни задачи, а **не** время работы. У людей с большой очередью (lead / cross-project owner) задача может неделями ждать в backlog'е — Velocity растёт, но это не «плохая оценка». **Velocity для leads — только secondary signal.**

**Caveat 2:** не учитываем парковку (`Приостановлено`, `Ждет фидбека` и пр.) — историю изменений статуса через MCP получить нельзя.

### 2. Deadline slip — отклонение от due_on

`completed_at − due_on` в днях, для задач где `due_on` заполнен. Метрики: `on_time_pct`, `late_pct`, `due_coverage_pct`.

**Caveat 3:** история изменений due_on недоступна. Если due_on проставлен в день закрытия — засчитаем как `on_time`, хотя реальный committed-due был раньше.

**Caveat 4:** частая коллективная норма — `late_pct = 0` у всех, `on_time` редко 100% (большинство задач закрываются до due_on). Значит due_on проставляется реактивно или с буфером.

### 3. QA return rate — `Отправлялось на доработку = Да`

% задач, которые QA заворачивали обратно. **Caveat 5:** поле заполняется не всегда — underreports.

## Сегментация

Главная: **assignee × discipline × issue_type**. Используй самую узкую сегментацию с ≥5 задачами, иначе расширяй: (assignee × discipline × issue_type) → (assignee × discipline) → (assignee) → (discipline × issue_type) → (discipline) → overall (low confidence).

`MIN_SAMPLE = 5`. Маленькая выборка — выводы индикативные, не доказательные.

## Ограничения данных (важно для интерпретации)

1. **Нет stories через MCP-коннектор** → не различаем committed-due и retroactively-changed-due; не знаем «когда взяли в работу».
2. **Estimate-поля почти не используются** → метрика actual/estimate ratio недоступна.
3. **`due_on` coverage обычно низкий** → deadline slip репрезентативен только для подмножества.
4. **Поле дисциплины часто разрежено** → сегментация по дисциплине страдает.
5. **Окно мало на старте** → у топ-исполнителей единицы задач на сегмент, а нужно 200+.

## Sensitivity policy

- Метрика **для PM-планирования рисков**. Не для performance review, не для рейтинга, не для эскалации в обвинительном формате.
- В публичных артефактах (status update, follow-up, Coda, draft'ы для upstream) **не цитировать персональные коэффициенты**. Допустимо: «по истории команды задача такого типа закрывается за P50 = Xd»; недопустимо: «у <человека> 67% QA returns».
- При 1-to-1 с исполнителем — его собственные данные в формате «помогает планировать», не «ты плохо оцениваешь».
- При обсуждении с upstream — обобщать на уровне команды/сегмента, без имён.

## Применение в работе

- При planning новой фичи → risk-adjusted длительность сегмента + индивидуальная коррекция.
- Внутри `feature-weekly-state` → флагать активные задачи где `days_since_created > segment.velocity_p80`.
- При estimate review с лидом → distribution по сегменту, не точечная оценка.
