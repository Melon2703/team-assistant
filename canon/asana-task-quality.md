# Asana Task Quality

> **Living document.** Working copy формальных правил заведения задач в Asana.
> Naming convention и discipline-split — универсальный паттерн. Префиксы, custom fields,
> collaborator-policy — `[TBD]`, заполните под свою taxonomy.

## Как пользоваться

- AI: читай этот файл при любом запросе про создание / правку / декомпозицию / review задач (вместе с Канон / team.md / focus.md).
- Человек: заводя задачу, прогоняй mini-checklist (раздел 6) **перед** сохранением.
- Любое расхождение этих правил с реальностью — сигнал обновить файл, не угадывать.

---

## 1. Зачем эти правила

Типичные повторяющиеся проблемы в задачах, которые эти правила лечат:

1. **Нет фокуса задачи.** Описание — копипаст из ТЗ; не выделено, что именно нужно сделать в этой конкретной задаче.
2. **Нет контекста билда.** В описание попадает то, что уже сделано, и то, что выносится отдельно (нотификации, тутор, аналитика, баланс).
3. **Нет вычитки.** Факты не соответствуют текущей реальности; пункты из чужой дисциплины.

Главный принцип: **AI задачи целиком не решит, финальное заведение — за человеком с feature-контекстом.** AI помогает draft-шаблоном; вычитка и ответственность за корректность — за PM.

---

## 2. Общие правила заведения

1. **Заводит человек с контекстом фичи.** AI — только помощник на draft. Никакого автоматического `create_tasks` без ручной построчной проверки.
2. **Каждую задачу валидирует `<TASK_REVIEWER>` (GD).** Добавляется как **collaborator** на каждой задаче, чтобы вычитка происходила до раздачи assignee'у. Без валидатора-collaborator задача не считается готовой к раздаче. `[TBD: кто валидатор в вашей команде]`.
3. **PM не добавляется как collaborator,** если задача явно не его (own admin-задачи: тех.тест, A/B, status update). Избегать дефолтного «всё под наблюдением PM» — перегружает inbox и стирает сигнал.
4. **Источники для задачи:** Primary — ТЗ фичи (live из Drive через `gdoc-fetch`); Secondary — план билдов (live); Опциональный — доп. контекст (Slack-решения). **Не источник:** другие задачи без атрибуции, «мы это где-то обсуждали».
5. **Обязательная вычитка перед сохранением** (mini-checklist, раздел 6).
6. **Архитектурные решения, влияющие на нарезку, фиксируются в `features/<feature>/decisions.md`.**

## 3. Naming convention

### 3.1. Базовый формат

```
(VERSION) PREFIX. [SUBPREFIX.] GOAL
```

- `VERSION` — `TS. Fix Version` в скобках. Критично: бот auto-routes задачи между проектами по этому полю. Без version задача застрянет в hub.
- `PREFIX` — устоявшаяся аббревиатура фичи. Не выдумывается — берётся из существующих задач проекта.
- `SUBPREFIX` (опц.) — указатель дисциплины / типа работы, см. 3.3.
- `GOAL` — понятна без открытия описания. Одна фраза.

### 3.2. Префиксы фич

`[TBD: таблица префиксов фич вашей команды]`. Пример:

| Фича | PREFIX | Пример |
|---|---|---|
| `<Фича A>` | `<PREFIX_A>` | `(3600) <PREFIX_A>. Подготовить сундук главной награды` |
| `<Фича B>` | `<PREFIX_B>` | `(3800) <PREFIX_B>. Оранжерея — финальный визуал` |
| Сабмит-задачи команды | `TS` | `(3600) TS. A/B-тест. <Фича A>` |

Если у фичи prefix непоследовательный — не выбирать сам, поднять с PM и зафиксировать в `features/<feature>/decisions.md`.

### 3.3. Subprefix по дисциплине

Когда задача относится к дисциплине и **разделение важно для scope**:

| Дисциплина | Subprefix | Когда |
|---|---|---|
| ART (UI) | `ART.` | Отрисовка визуала, макеты, иконки, окна |
| Programming | `Code.` или без (default) | Вставка UI, логика, корнер-кейсы |
| VFX | `VFX.` | Анимации, эффекты, флоу |
| Game Design | `GD.` | Концепты, баланс, ТЗ-уточнения |
| QA | `QA.` | Тесткейсы, чеклисты, регрессия |
| Tech Design | `TD.` | Verstka, UI Kit |
| Тех. тесты | `Тех. тест.` | A/B, технические тесты |

Subprefix **не дублирует** поле дисциплины — он нужен в названии, чтобы при беглом scan'е видеть, какие задачи блочат друг друга по дисциплине. `[TBD: адаптируйте под свои дисциплины]`.

### 3.4. Разделение UI и вставки программистом

**Центральная норма для build-skeleton фич.** Частая боль — задачи смешивают art и code.

- **ART — отдельная задача** с subprefix `ART.` и дисциплиной ART. Goal — observable artifact («финальный визуал X в Figma + 4 иконки в Drive»).
- **Programming — отдельная задача** (default без subprefix или `Code.`). Goal — observable result в билде. Имеет **blocked-by** связь с ART-задачей.
- В описании programming-задачи — ссылка на ART-задачу; в ART-задаче — куда пойдёт результат.

Не допускается: одна задача на «ART + Code»; programming-задача со scope'ом «сделать UI и вставить» — это две задачи.

### 3.5. Anti-patterns в названиях

| Плохо | Почему | Хорошо |
|---|---|---|
| `Билд 3 - Оранжерея` | Нет version/prefix, бот не auto-route | `(3800) <PREFIX>. Оранжерея — финальный визуал` |
| `Сделать оранжерею` | Goal размытый, не observable | `(3800) <PREFIX>. Оранжерея — смена визуала дерева при апгрейде` |
| `(3800) <PREFIX>. Оранжерея + нотификации + тутор` | Несколько scope'ов | Три задачи: визуал / нотификации / тутор |
| `(3800) <PREFIX>. ART и Code на фабрику` | Смешаны дисциплины | Две задачи: ART визуала + Code пересборки |

## 4. Description template

```markdown
**Цель задачи (одно предложение):**
<Что должно работать / появиться / быть проверяемым после закрытия.>

**Acceptance criteria:**
- [ ] <Observable условие 1 — то, что QA / GD / PM может проверить>
- [ ] <...>

**Источники:**
- ТЗ: <ссылка на Google Doc с heading-anchor, НЕ копипаст>
- План билдов: <ссылка с heading-anchor>
- Концепт / Miro: <если релевантно>
- Slack-решение: <ссылка на тред, если есть архитектурное / GD-решение>

<!-- Если контекст неполный — оставить тег ниже, иначе удалить -->
@<TASK_REVIEWER> — прошу дополнить: <конкретный пункт>
```

### 4.1. Правила заполнения

- **Цель — одно предложение.** Не помещается — задача слишком большая.
- **Acceptance criteria — observable.** Не «оранжерея работает», а «при достижении этапа N меняется визуал дерева; иконка апгрейда исчезает». Каждый пункт проверяем без звонка автору.
- **Источники — ссылки, не цитаты.** Heading-anchor на нужный раздел. Всегда добавлять Slack-тред, если есть влияющее решение.
- **Тег валидатора — только когда контекст неполный.** Явный action дополнить, не decorative.

## 5. Anti-patterns в описании

| Anti-pattern | Почему плохо | Что делать |
|---|---|---|
| **Копипаст раздела ТЗ целиком.** | Исполнитель не понимает, что относится к задаче. QA переспрашивает. | Ссылка на раздел + 2-3 буллета релевантного. |
| **Смешивание scope'ов** (окно + нотификации + тутор). | Исполнитель тратит время на ненужное сейчас или пропускает. | Каждая логическая единица — отдельная задача. |
| **Пункты из чужой дисциплины** (spine в задаче программисту). | Не может сделать чужую работу. Переспрос или кривая реализация. | Проверить, что все пункты — дисциплина assignee'я. Учесть `features/<feature>/decisions.md`. |
| **Описание противоречит обсуждению в Slack.** | Исполнитель решает не ту проблему. Всплывает на QA. | Проверить feature-канал за последние 3-5 дней. Отразить в «Источники → Slack». |
| **`[TBD]` без явного тега валидатора.** | Orphan expectation, никто не возьмёт. | Явно `@<TASK_REVIEWER> — прошу дополнить: <что>`. Без тега `[TBD]` запрещён. |
| **AC «сделать», «реализовать», «поправить».** | Не observable. Бесконечные туда-обратно с QA. | Переформулировать в «при действии X происходит Y». |
| **`[Duplicate]` без ссылки на оригинал в комментарии.** | При сверке готовности Duplicate не считается закрытой; контекст/фидбэк теряется. | Закрывая как Duplicate — комментарий со ссылкой на оригинал. При работе с Duplicate читать комментарии. |

### Правила, связанные с feature-build flow `[наблюдение]`

- **QA-задачи на feature-build не заводятся** (если по практике вашей команды QA смотрит задачи ребят и оставляет фидбэк там же). Исключения — общие QA-инструменты (тесткейсы, регрессионные чек-листы). `[TBD: подтвердите под свой процесс]`.
- **Зависимости между задачами — через Asana field `dependencies`, не текстом в описании.** В описании зависимости упоминать только если нужно объяснить логику.
- **Структурные контейнеры активного плана — исключение из «не создавать задачи автоматически».** Когда задачи нужны как `subtask`-группировки эпиков для зеркала структуры gdoc-плана — допустимо создавать через `create_tasks` по запросу PM. Применяется к **структурным группировкам**, не к feature-задачам.

## 6. Mini-checklist перед сохранением задачи

Если хоть один «нет» — задача не готова.

- [ ] Название по формату `(VERSION) PREFIX. [SUBPREFIX.] GOAL`.
- [ ] Goal понятен без открытия описания.
- [ ] Обязательные custom fields заполнены `[TBD: ваш список]`.
- [ ] Assignee назначен (или явно тег валидатора, если scope неясен).
- [ ] `<TASK_REVIEWER>` добавлен как collaborator.
- [ ] Описание следует template: Цель + Acceptance criteria + Источники.
- [ ] AC observable.
- [ ] Источники — ссылки с heading-anchor, не копипаст. Slack-тред добавлен если есть.
- [ ] Все пункты описания — дисциплина assignee'я.
- [ ] Проверен `features/<feature>/decisions.md` — нет противоречий.
- [ ] Нет противоречий с обсуждениями в feature-канале за 3-5 дней.
- [ ] PM НЕ добавлен как collaborator (кроме своих admin-задач).

## 7. Best practices reference

Generic industry baseline (без атрибуции конкретных компаний):

- **INVEST** (Bill Wake): Independent, Negotiable, Valuable, Estimable, Small, Testable. Критичнее всего — **Small** (1-3 дня) и **Testable** (observable AC).
- **Acceptance criteria в Given/When/Then** (Gherkin) — стандарт QA-driven команд. Жёсткий Gherkin не обязателен, observable — обязательно.
- **Discipline split** — стандарт AAA pipelines (UI отдельно от Code, VFX от Animation). Цель — каждая задача делается одним человеком в одну сессию.
- **Один scope — одна задача.** ≥2 observable artifact'а из разных дисциплин → две задачи через `Blocked by`.
- **1-3 дня на задачу — норма.** Больше — декомпозируется. Меньше 0.5 дня — кандидат на объединение.
- **Definition of Ready** перед стартом = mini-checklist раздела 6.
- **Definition of Done** перед «Готово» — `[TBD: зафиксируйте для команды: AC + QA pass + PR merged?]`.

## 8. Что NOT делать — суммарно

- Не заводить AI-generated задачи в Asana автоматически.
- Не копировать раздел ТЗ целиком.
- Не смешивать дисциплины (UI + Code, Programming + Animation).
- Не смешивать scope'ы разных билдов.
- Не оставлять `[TBD]` без явного тега валидатора.
- Не добавлять PM collaborator по умолчанию.
- Не использовать названия без version / prefix.
- Не игнорировать решения из `features/<feature>/decisions.md`.
