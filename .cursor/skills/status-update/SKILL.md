# Status Update

Составить draft status update по фичам команды в формате, который PM реально использует в Asana project status. Cadence — настраивается под команду (в исходной — bi-weekly, раз в 2 недели).

> Формат, tone, чек-листы вырезания внутрянки — универсальная методология.
> Конкретные фичи / версии / имена в примерах — placeholder, замените под свою команду.

## КРИТИЧНО: формат публикации vs формальный template

Часто формальный template (Coda / wiki) описывает формат с маркерами ✅/⚠️/❗ и %-готовности. На практике он может **не использоваться** — реальный формат проще. Зафиксируйте фактический формат своей команды здесь. Ниже — формат исходной команды (плоский bullet list, без маркеров, без процентов).

## Формат вывода (повторяй точно)

```
Всем привет! 👋

Что сделали за последнее время:

**<Фича 1>**
- <Высокоуровневое достижение, обезличенно>
- ...

**<Фича 2>**
- ...

(опционально)
**Улучшение процессов**
- <Только если есть что сказать stakeholder-аудитории>

(опционально)
**Организационное**
- <HR-сигналы, релевантные внешней аудитории — выход нового разработчика, смена ownership>

---

План на следующие 2 недели (DD.MM – DD.MM)

**<Фича 1>**
- <Конкретный milestone, можно с датой>

**<Фича 2>**
- <Можно с вложенным списком модулей через двоеточие, если это план билда>

Держим вас в курсе!
(опционально: А ниже немного красивых промежуточных артов будущей фичи 😍)
```

### Правила формата

- Период «что сделали» — без явной шапки с датами.
- Период «план» — обязательно с датами в скобках: `(DD.MM – DD.MM)`.
- Bullet list плоский. Вложенные bullets — только когда раскладываешь скоуп билда по дисциплинам (Верстка / VFX / Контент) или по модулям.
- **Никаких** ✅/⚠️/❗ маркеров. **Никаких** %-готовности.
- **Никаких** ссылок на конкретные Asana-задачи, Slack-треды, Google Docs внутри финального текста.
- **Никаких** конкретных дат «за последнее время». Конкретные даты — только для будущих milestone'ов.

### Шаблон раскрытия плана билда

Когда фича в стадии MVP / финализации билда (есть конкретный план в Drive) — раскрывай план по дисциплинам:

```
**<Фича>**
- Метим следующий билд (<MVP N>) на DD.MM. В билд планируем зафиналить:
  - Верстка:
    - <окна / экраны>
  - VFX:
    - <анимационные блоки>
  - Контент:
    - <здания, персонажи, анимации локаций>
  - Финальные туториалы (если в скоупе)
- <опционально: общий пункт про экономику / архитектурное изменение>
- Параллельно начинаем планировать скоуп после <билда>
```

Правила: дисциплины — только если в них есть скоуп (пустые секции не показываем); источник scope — план билдов (см. «Что прочитать»); внутри дисциплины — high-level названия модулей, без под-задач и имён. Когда фича не в стадии раскладки билда — план остаётся плоским bullet list.

## Tone

- Дружеский, командный («мы собрали», «доделали»), не отчётный PM-голос.
- 👋 в открытии — стабильно. 😍 в конце — только если прикладываются арты.
- Не благодарить, не извиняться, без «успешно завершили», «проактивно», «синергично».
- Числа > эпитеты, но цифр мало (публикация для широкой аудитории, не PM-репорт).
- Прямо и просто.

## Open vs decided GD-решения

В апдейт попадают **только зафиксированные** решения. Для решений в обсуждении — обобщай.

**Decided (можно публиковать конкретно):** зафиксировано `<!channel>` в feature-канале; лежит в `current/decisions.md` / `features/<feature>/decisions.md`; в Asana закрытая корневая задача с финальным заключением; в overview встречи — Action Item с конкретной формулировкой и owner'ом.

**Open / re-opened (публикуй обобщённо):** в overview помечено «отложено», «N вариантов»; решение в одном источнике, но в более свежем снова варианты на столе; активная дискуссия без финального `<!channel>`.

**Как обобщать:** конкретику игровой механики при open-статусе → высокоуровневая формулировка («упрощаем модель прогресса», «упрощаем экономику», «пересобираем флоу обучения»). В блоке «Что нужно уточнить» **обязательно** отмечай open-решения с альтернативами.

## Паттерн: AB-тест

Когда в окне апдейта запущен / мониторится AB-тест:

**При запуске:** `- Запустили долгий AB-тест на проде, тест идёт по N группам (~K игроков)` — N = число групп, K = размер выборки округлённо. Источник — root-задача AB в Asana. **НЕ публиковать**: гипотезу, MDE, target-метрики, пороги success / guardrail, списки исключений, платформы / регионы.

**При мониторинге:** `- Получаем первый срез результатов AB-теста (~DD.MM), смотрим направление по гипотезе` — формулировка намеренно обтекаемая.

**При закрытии:** успех → «направление подтвердилось, катим»; неуспех → «корректируем подход» (без деталей). Конкретные числа ARPU / Retention — **не публиковать**.

## Что ВЫРЕЗАТЬ перед публикацией (важно)

Финальный апдейт идёт **широкой stakeholder-аудитории**. Удаляется вся «внутрянка»:

- **Имена членов команды по фамилиям.** «X финализировал балансы» → «финализировали балансы». Безличное «мы / команда».
- **Имена upstream stakeholders** — продюсер, директора, cross-team координатор, имена из overview встреч. Обезличенно («первый внешний просмотр», «получаем фидбэк»).
- **Конкретные даты прошедших событий.** Только для будущих milestone'ов.
- **Конкретные баги, баг-IDs, тех. детали.** Обобщи: «закрыли финальные кейсы по тех. тесту».
- **Внутренние процессные инициативы** (сбор фидбэка по флоу, peer-1to1) — только если это HR-/scale-сигнал внешней аудитории.
- **Конфликты, риски, blockers.** Это для внутренних обсуждений, не для апдейта.
- **Технические детали инфраструктуры** (git-ветки, build numbers, имена пайплайнов) — только high-level.
- **HR-чувствительное** (кто в отпуске, перегрузка, болезни). Исключение — выход нового разработчика, передача ownership (в «Организационное»).
- **Web-payments parameters, A/B holdout details, бизнес-числа.**
- **AB-sensitive параметры** — гипотезы, пороги метрик, success-критерии, платформы / регионы / списки исключений. Структурные (число групп, размер выборки, дата среза) — можно.
- **Конкретные mechanics-формулировки** — специфические UI-элементы, конкретные шаги туториалов. Обобщай.
- **Gameplay-параллели с другими играми** — конкретные референсы. Не публиковать.

### Исключение: tooling / AI-эксперименты — когда публикуем

Обычно «внутрянка», но **публикуем**, если все 3 условия: (1) новая практика / эксперимент; (2) влияет на скорость работы или открывает новый класс задач; (3) можно сформулировать обезличенно. Шаблоны: «Начали пробовать `<X>` для `<задачи>` (пилот)», «Перешли на новый пайплайн `<название>` — `<выигрыш>`». Если результата ещё нет — отметь в «Что нужно уточнить».

## Что прочитать перед составлением

### 1. План билдов — делать первым (блокирующий источник)

Без плана нельзя раскрыть «План на 2 недели» по дисциплинам. 3-stage fallback:

1. **Live через `user-google` MCP** (см. `gdoc-fetch`) по ссылке из `features/<feature>/README.md`. Предпочтительный путь.
2. **Если MCP не вернул данные** — локальная копия (если есть), но **явно отметь**: «Использовал локальную копию, может быть устаревшая».
3. **Если нет ни live, ни локально** — **остановись и спроси**. Не угадывай scope.

### 2. Остальное (в порядке приоритета)

1. **Предыдущие status update драфты** (`current/status-update-draft-YYYY-MM-DD.md`) — главный источник стиля. Читай 1-2 последних.
2. `current/focus.md` — текущий фокус. Если устарел (>7 дней) — флагай.
3. **Asana** — для каждой фичи: open count, key модули, последние изменения. Для AB — root-задача (число групп, выборка, дата среза; гипотеза/метрики в апдейт не идут).
4. **Slack feature-каналы** — milestones, `<!channel>`, build-merge.
5. **Slack `<TEAM_PROD_CHANNEL>`** — status-чеки producer'а.
6. **Доп. контекст от пользователя** (overview встречи, заметки) — primary source для актуальных GD-обсуждений.

## Структура файла-драфта

Имя: `current/status-update-draft-YYYY-MM-DD.md` (дата = дата публикации).

```markdown
# Статус-апдейт — DD.MM.YYYY

Период: DD.MM – DD.MM.YYYY (2 недели после прошлого апдейта DD.MM).
Стиль и структура: повторяет апдейт от <prev_date>.

---
<сам текст апдейта, готовый к копированию в Asana>
---

## Что нужно уточнить перед публикацией
<секция уточнений, см. ниже>

---

**Проверка обновлений контекста:**
<self-update check блок согласно .cursor/rules/00-bootstrap.mdc>
```

### Секция «Что нужно уточнить перед публикацией»

Каждый ambiguous момент — отдельным пунктом, **обязательно с альтернативами A vs B**. Категории: Имена; Конкретные даты прошедших событий; Open GD-решения; Sensitive-параметры (AB); Новые tooling-практики; Перенос пунктов из прошлого апдейта; Детализация плана билда.

Формат: `- **<Тема>.** <Контекст в 1 предложении.> Сейчас в draft: <вариант A>. Альтернатива: <вариант B>.`

## Output

1. Ты выдаёшь draft в `current/status-update-draft-YYYY-MM-DD.md`.
2. PM вычищает имена / даты / внутрянку, отполировывает.
3. PM копирует в Asana project status.

Шаг 1 — твоя зона. Шаги 2-3 — PM сам.

## Если данных не хватает

Не угадывай. Перечисли явно в «Что нужно уточнить». Лучше draft на 60% с `[уточнить: X]`, чем красивый текст с выдуманными числами.

## Antipatterns

- ❌ Внутрянка в финальном тексте (имена, mechanics, конкретные даты прошедших событий, Asana ID / Slack-ссылки, баги, маркеры, %-готовности).
- ❌ План билда из локальной копии без проверки live-fetch.
- ❌ Явная финальная формулировка open / re-opened GD-решения.
