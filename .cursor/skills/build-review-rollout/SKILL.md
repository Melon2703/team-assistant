# Build Review Rollout

Создать подзадачи на просмотр билда из корневой задачи.

> Имя корневой парсится regex'ом. Формат имени и шаблон подзадачи — настраиваемые под команду
> (`[TBD: ваш ROOT_NAME_PATTERN]`). Ниже — пример из исходной команды: `(VERSION) PREFIX. Билд N`.

Pre-state — корневая задача со скелетом технических подзадач (`() Просмотр билда.`, `() Просмотр билда. Ветка для просмотра. Сборка билда`, `() Просмотр билда. Подготовить описание что смотреть`, `() Просмотр билда. Проверить билд перед отправкой`) и шаблонным описанием — заводится отдельно из template'а Asana, не этим skill'ом.

## Inputs

1. **Корневая задача** — Asana URL или GID.
2. **Список просматривающих** — список `Имя Фамилия` через запятую / перенос строки / маркеры, как в Asana.

Если хотя бы один вход не задан — **спроси, не угадывай**. Особенно список людей: молча вытаскивать из контекста чата нельзя.

Опционально: **Working days offset** — по умолчанию `3 рабочих дня вперёд`. Если задан другой — учти.

## Critical pre-flight gate: GD заполнил описание корневой?

Самый важный gate. Раскатывать пустой шаблон бесполезно — у просматривающих не будет контекста.

1. `get_task(task_id=<root_gid>, opt_fields="name,notes,html_notes,parent.gid,subtasks.gid,subtasks.name")`.
2. **Проверь, что задача — корневая на просмотр:**
   - `parent` should be `null`.
   - `name` matches `[TBD: ROOT_NAME_PATTERN]` (пример: `^\((\d{3,4})\)\s+(.+?)\.\s+Билд\s+(\d+)`) — извлеки `version`, `prefix`, `build_number`. Если не матчится — стоп, флагай.
3. **Проверь, что описание заполнено** (не плейсхолдер). В `notes` / `html_notes` ищи маркеры незаполненного шаблона (пример): `[ссылка на головную задачу фичи]`, `[ссылка на билд]`, `[Например:`, `[как запустить]`, `[что сделано в билде и поинты`, `[поинты, которые еще не готовы]`.

   Если **любой** плейсхолдер остался — GD ещё не заполнил. **Стоп**, сообщи:

   ```
   GD ещё не заполнил описание корневой задачи. В шаблоне остались плейсхолдеры:
   - [...]
   Перед раскаткой нужно: попросить GD заполнить корневую. После заполнения — повтори запрос.
   ```

4. **Sanity check:** есть ли build-ссылка и блок «Цель» / «На что смотрим». Если описание заполнено, но очень короткое (< 200 символов) — флагай как possible-incomplete и **спроси**, продолжать ли.

## Алгоритм раскатки

### 1. Извлечь параметры из имени корневой

Через regex (пример): `^\((\d{3,4})\)\s+(.+?)\.\s+Билд\s+(\d+)(?:\s*[-–—]\s*(.+))?$` → `version`, `prefix`, `build_number`, `build_suffix` (опц.).

Имя финальной подзадачи: `(VERSION) PREFIX. Билд N. Просмотр билда. <Имя Фамилия>`. `build_suffix` в имена подзадач по умолчанию **не включаем** (единообразие).

### 2. Найти assignee для каждого имени

1. `search_objects(resource_type="user", query="<Имя Фамилия>", count=5)`.
2. Match strategy: exact match на `name` (case-insensitive) — приоритет. Несколько тёзок — **спроси**, не угадывай (покажи email/GID). Ноль — попробуй reverse order (`Фамилия Имя`). Опять ноль — `not_found`, не блокируй остальных.
3. Запомни `user_gid`.

### 3. Вычислить due_on (N рабочих дней вперёд)

```
start = today
n = 3 (или явный offset)
d = start
while n > 0:
    d = d + 1 day
    if d.weekday() in [0..4]:  # Mon..Fri
        n -= 1
return d
```

Праздники не учитываем (нет общего календаря). `due_on` форматируется `YYYY-MM-DD`.

### 4. Скопировать описание корневой

Получаем `html_notes` корневой (приоритет над `notes`). Это описание для **каждой** новой подзадачи.

### 5. Создать новые подзадачи через `create_tasks`

Один batch-запрос. Для каждой: `name`, `parent=<root_gid>`, `html_notes=<root_html_notes>`, `assignee=<user_gid>` (пропустить если `not_found`), `due_on=<computed>`.

Custom fields **не выставляем** — подзадачи просмотра их обычно не имеют.

### 6. (Опционально) Скопировать описание в существующие технические подзадачи

По требованию. Для каждой pre-existing скелетной подзадачи — `update_tasks` с новым `html_notes`. **Не трогай** их `name`, `assignee`, `due_on`. Если сказано «только новые» — пропусти.

## Confirm перед write

Write-операция в Asana. Перед `create_tasks` / `update_tasks`:

1. Покажи **полный preview**: корневая (name, link, выдержка описания); список новых подзадач (name, assignee + email, due_on); список pre-existing для копирования; `not_found` отдельно.
2. Жди явного «ок» / «поехали».
3. Только после — вызывай.

Per `.cursor/rules/01-actions-policy.mdc` — типовой повторяющийся flow со scope в одной корневой задаче не требует second confirmation для bulk, но один confirm обязателен.

## Output

```markdown
# Build Review Rollout — <prefix> Билд N

**Корневая:** [<name>](<url>)
**Дата раскатки:** YYYY-MM-DD · **Due:** YYYY-MM-DD (+N раб. дн.)

## Созданы подзадачи (N)
- ✓ [(VERSION) PREFIX. Билд N. Просмотр билда. <Имя>](<url>) — assignee <Имя>, due YYYY-MM-DD
- ⚠ [... <Имя>](<url>) — assignee NOT FOUND, due YYYY-MM-DD (назначить вручную)

## Описание скопировано в pre-existing подзадачи (M)
## Что не получилось
```

## Что НЕ делать

- **Не запускать без подтверждения, что GD заполнил описание корневой.** Hard gate, без exception.
- **Не угадывать assignee при тёзках.** Спросить.
- **Не назначать upstream stakeholders на просмотр silent** — если в списке новое имя, которого не было в прошлых раскатках, флагни «это новое имя, подтверждаешь?».
- **Не плодить дубли.** Если уже есть подзадача `Просмотр билда. <Имя>` — не дублируй, флагни.
- **Не менять описание корневой.** Только читаем.
- **Не менять `name` / `parent` / `due` у pre-existing технических подзадач.** Только `html_notes`.
- **Не трогать `delete_task` ни при каком сценарии.**

## Edge cases

- Неверный GID — `get_task` вернёт ошибку, останови.
- Корневая — subtask (`parent != null`) — флагни, спроси ссылку на root.
- `build_number` не извлёкся — флагни, спроси подтверждения.
- Список сильно отличается от прошлой раскатки — sanity check, спроси.
- Праздник в окне +N раб. дней — skill не учитывает, PM поправит вручную.
- `html_notes` содержит data-asana-gid links на пользователей — копируй as-is.
