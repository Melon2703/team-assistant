# PRD: Контур — операционный слой контекста по фичам

*Версия: 0.2. Владелец: Данила. Читатели: Стас, команда «Паспорта фичи», PM/менеджеры команд, потенциальная разработка.*

## 1. TL;DR

**Контур** помогает PM и команде понимать, что реально происходит с фичей, не собирая вручную контекст из Asana, Slack, Google Docs и «Паспорта фичи».

На первом этапе Контур должен уметь:

1. собрать состояние фичи на текущий момент;
2. подсветить риски, незакрытые вопросы, мискомы, неправильное понимание или смещение приоритетов;
3. сгенерировать статус-апдейт за последние 2 недели;
4. завести задачи в Asana на основе Плана Билдов, ТЗ и дополнительного контекста;
5. ответить на конкретный вопрос по фиче.

Главный принцип:

> **Claude не должен каждый раз заново ходить по всем источникам и читать весь сырой контекст. Контур заранее собирает и поддерживает память фичи, а Claude получает короткий context packet под конкретную задачу.**

## 2. Проблема

Сегодня состояние фичи живёт в разных местах:

- метрики и сроки — в «Паспорте фичи»;
- План Билдов и ТЗ — в Google Docs;
- задачи, комментарии, owners и статусы — в Asana;
- решения, сомнения, мискомы и приоритеты — в Slack;
- технические и outcome-сигналы — потенциально в GitHub, AllBuilds, Amplitude/AB.

Из-за этого PM тратит время на ручной сбор картины, а важные нюансы коммуникации могут не попасть в формальные метрики.

## 3. Продуктовая ставка

1. **Не заменяем «Паспорт».** «Паспорт» остаётся источником проверенных метрик: сроки, размер, попадание в план, качество.
2. **Не слепнем на цифрах.** Контур читает raw evidence из Asana, Slack и Google Docs, потому что именно там живут решения, сомнения, мискомы и нюансы.
3. **Не строим чат-бота ради чат-бота.** Строим набор рабочих PM-флоу вокруг фичи.
4. **Экономим токены контекстом.** Сначала создаём feature memory и context packets, затем вызываем Claude.
5. **Сначала польза PM, потом управленческие сводки.** Верхний слой появляется после доказанной пользы на одной команде.

## 4. Персоны

### PM / менеджер фичи

Хочет быстро понимать состояние фичи, получать статус-апдейты, видеть риски и заводить задачи без ручного копания в источниках.

### Руководитель / топ-менеджер

Хочет честную картину по продакшену без ручного сбора статусов и без токсичного сравнения «продуктивности» команд.

### Команда «Паспорта фичи»

Хочет, чтобы новый слой не дублировал уже сделанные метрики и не конкурировал с «Паспортом».

### Будущая разработка / платформа внутренних AI-tools

Хочет понятную архитектуру: где данные, где workflow, где Claude API, где rights/permissions, где evals и observability.

## 5. Набор функций v0.2

### 5.1. Состояние фичи на текущий момент

**Вопрос пользователя:** «Что сейчас происходит с фичей X?»

**Контур отвечает:**

- где фича находится относительно плана;
- какие последние важные изменения;
- какие решения подтверждены;
- какие вопросы открыты;
- какие риски активны;
- чего не хватает, чтобы картина была полной;
- **что система НЕ видит** (coverage / blind-spots: неподключённые каналы, нечитаемые источники);
- ссылки на источники.

**Успех:** PM за 2–3 минуты получает рабочую картину фичи без ручного обхода Asana/Slack/GDocs и понимает, насколько она полная.

### 5.2. Риски, незакрытые вопросы, мискомы и смещение приоритетов

**Контур подсвечивает:**

- build/risk: билд должен быть готов, но evidence говорит обратное;
- open question: вопрос висит без owner или решения;
- miscommunication: разные источники по-разному понимают одно решение;
- priority drift: команда обсуждает или делает не то, что зафиксировано в плане;
- stale plan: План Билдов не обновлён, но коммуникация уже ушла дальше.

**Успех:** PM получает ранний сигнал до того, как риск стал фактом задержки.

### 5.3. Статус-апдейт за последние 2 недели

**Контур генерирует черновик:**

- что изменилось за 2 недели;
- где мы относительно плана;
- какие решения приняты;
- какие вопросы открыты;
- какие риски появились или закрылись;
- что нужно от PM/лида/руководства;
- что неизвестно или требует подтверждения.

**Успех:** PM принимает черновик с минимальной правкой.

### 5.4. Заведение задач в Asana на основе Плана Билдов и ТЗ

**Контур предлагает:**

- структуру задач по билдам;
- задачи на подготовку билдов;
- задачи на открытые вопросы или риски;
- missing tasks, если План Билдов требует задач, которых нет в Asana;
- owners/due dates, если их можно вывести из контекста.

**Важно:** на MVP Контур не создаёт задачи автономно. Он готовит draft, PM подтверждает, только потом система пишет в Asana.

**Успех:** PM экономит время на декомпозиции и снижает риск забытых задач.

### 5.5. Ответ на конкретный вопрос по фиче

**Примеры вопросов:**

- кто занимается X;
- когда будет готово Y;
- что не хватает для Z;
- почему фича выглядит по «Паспорту» нормально, но в коммуникации видно, что она буксует;
- какие решения по scope были приняты за последние 2 недели;
- что нужно сделать до следующего билда.

**Успех:** ответ grounded: у важных утверждений есть source references, а неизвестное явно помечено как unknown.

## 6. Что сознательно не делаем в MVP

- не строим полную агентную платформу;
- не даём Claude автономно писать в Asana/Slack;
- не индексируем весь Slack workspace сразу;
- не строим полный knowledge graph;
- не сравниваем productivity команд;
- не делаем local LLM как основной backend;
- не пишем ни байта в Raw Evidence Store до закрытого governance (см. `07`, D8);
- не строим managed-инфру до пройденного Phase −1 на дешёвом сетапе (см. `05`, `06`).

## 6.1. Жёсткие констрейнты

- **Governance до данных.** Контур создаёт новый агрегированный sensitive-стор. Sensitivity — на уровне источника, `permission_label` enforce'ится на query time, redaction на выходе — второй слой. Закрывается до ingestion, не «по ходу».
- **Honesty про покрытие.** Любой ответ несёт coverage / blind-spots. Уверенный вывод по неполной картине без пометки — баг, а не фича.

## 7. Метрики успеха

### Польза PM

- часы, сэкономленные на статусах и сборе контекста;
- доля принятых статус-черновиков;
- число полезных ранних рисков;
- число закрытых open questions / miscoms;
- время на заведение задач по новой фиче до/после.

### Качество

- **PM acceptance / edit distance — метрика №1** (это и драйвер окупаемости, см. `06`);
- доля важных утверждений с source reference;
- coverage / blind-spot honesty: доля ответов с честной пометкой покрытия;
- extraction precision (доля полезных кандидатов, не шум);
- factuality issues;
- redaction issues;
- stale context incidents.

### Экономика

- стоимость Claude API на один workflow run;
- стоимость хранения и ingestion;
- **realization factor** (gross vs net сэкономленного времени);
- COGS: build (one-time) + maintenance (recurring), break-even по числу PM (см. `06`);
- value of time saved (net, с discount);
- стоимость tokens saved (вторично, копейки на 1 PM).

## 8. Термины

**Raw Evidence** — сырой источник: Slack-тред, Asana-комментарий, Google Doc-секция, запись из «Паспорта».

**Extracted Artifact** — структурированный вывод из evidence: decision, risk, open question, miscommunication, blocker, scope change.

**Feature Memory** — актуальное состояние фичи, собранное из подтверждённых и кандидатных артефактов.

**Context Packet** — короткий пакет контекста для Claude под конкретную задачу.

**Workflow** — заранее заданная цепочка шагов.

**Agent Mode** — режим для vague investigation, где Claude может сам выбирать read-only tools в рамках лимитов.

**Coverage / Blind-spots** — какие источники система видит по фиче и какие точно НЕ видит. Часть каждого ответа.

**Discrepancy / Diff Engine** — компонент, считающий расхождения (план↔коммуникация, было↔стало, source_A↔source_B), а не суммаризирующий.
